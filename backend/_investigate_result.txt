排查结论如下。代码中没有发现“协议正常、Hub 成功路径漏调用广播”的直接证据；但发现了明确的终态命名不一致、结果帧解析过窄，以及事件通道本身存在可预期丢事件的设计。

**1. Hub 的成功和失败路径**

在 [`src/hub/relayHub.ts:367`](G:/msgrelay/src/hub/relayHub.ts:367) 的 `handle_result` 中：

- 节点结果先检查任务是否存在、节点是否匹配、`generation` 是否匹配。
- `frame.ok === false` 时进入 [`fail_task`](G:/msgrelay/src/hub/relayHub.ts:385)。
- `frame.ok` 不是 `false` 时调用 `this.tasks.finish(...)`。
- 成功完成后明确调用：

```ts
this.publish_task_event('task.done', done);
```

位置在 [`src/hub/relayHub.ts:390-400`](G:/msgrelay/src/hub/relayHub.ts:390)。

失败路径也明确广播：

```ts
this.publish_task_event('task.failed', failed);
```

位置在 [`src/hub/relayHub.ts:407-415`](G:/msgrelay/src/hub/relayHub.ts:407)。

因此，**对于当前协议中使用 `ok: true/false` 的节点，Hub 的 succeeded 成功路径和 failed 失败路径都存在广播调用，没有发现一条明显漏发路径**。

但是这里有一个明确的协议兼容问题：

```ts
if (frame.ok === false) {
  ...
}
```

`handle_result` 不读取 `frame.status`。也就是说：

- `status: 'succeeded'`、但没有 `ok: false`：会按成功处理，最终广播 `task.done`；
- `status: 'completed'`、但没有 `ok: false`：也会按成功处理；
- `status: 'failed'`、但没有 `ok: false`：同样会被当成成功处理，存在错误上报被误判为成功的风险；
- `status: 'done'`：会被当成成功，但广播名称仍然是 `task.done`。

节点自身的 [`src/nodes/nodeAgent.ts:409-420`](G:/msgrelay/src/nodes/nodeAgent.ts:409) 使用的是 `ok: true/false`，所以如果所有实际节点都通过 `nodeAgent` 上报，当前代码可以正常工作。是否存在 Codex/OpenCode 节点直接发送 `status=succeeded/completed/failed`，需要查看运行时原始帧日志确认。

**2. 协议中没有 `succeeded` 或 `completed` 事件**

[`src/protocol/types.ts:64-78`](G:/msgrelay/src/protocol/types.ts:64) 定义的 `relay_frame` 只是：

```ts
export interface relay_frame {
  type: string;
  [key: string]: unknown;
}
```

代码没有单独的 `result_frame` 类型，也没有对结果帧的 `status` 字段做类型约束。

任务状态机只定义了：

```ts
queued
assigned
running
done
failed
cancelled
expired
```

具体见 [`src/protocol/types.ts:70-78`](G:/msgrelay/src/protocol/types.ts:70)。

因此：

- 没有 `succeeded` 任务状态；
- 没有 `completed` 任务状态；
- 没有 `task.succeeded` 事件；
- 没有 `task.completed` 事件；
- 成功事件的正式名称是 `task.done`。

设计文档也明确只列出：

```text
task.queued
task.started
task.progress
task.done
task.failed
task.cancelled
task.expired
node.online
node.offline
```

见 [`docs/协议说明.md:83-91`](G:/msgrelay/docs/协议说明.md:83)。

所以，如果主会话或上层系统等待的是 `task.succeeded` 或 `task.completed`，那么这是一个**确定的事件名称不匹配问题**，不是偶发网络问题。

如果要兼容这些名称，建议在 [`src/hub/relayHub.ts:367-400`](G:/msgrelay/src/hub/relayHub.ts:367) 的成功收尾分支，或者更集中地在 [`publish_task_event`](G:/msgrelay/src/hub/relayHub.ts:554) 处建立统一映射：

```text
内部状态 done
→ 对外主事件 task.done
→ 如确需兼容，再额外提供 task.succeeded/task.completed
```

但需要先确认主会话实际监听的事件名称，避免同时广播多个终态事件造成重复通知。

**3. `taskStore` 只负责改变状态，不负责广播**

[`src/hub/taskStore.ts:151-158`](G:/msgrelay/src/hub/taskStore.ts:151) 将任务从 `assigned` 转为 `running`。

成功收尾在 [`src/hub/taskStore.ts:176-194`](G:/msgrelay/src/hub/taskStore.ts:176)：

- 检查任务是否已经是终态；
- 检查附件是否全部收齐；
- 设置 `task.status = 'done'`；
- 设置进度为 `100`；
- 写入 `finishedAt`；
- 返回任务。

失败收尾在 [`src/hub/taskStore.ts:197-210`](G:/msgrelay/src/hub/taskStore.ts:197)：

- 设置 `task.status = 'failed'`；
- 设置错误信息；
- 写入 `finishedAt`；
- 返回任务。

这些方法本身**不触发事件通知**。事件由调用它们的 Hub 或 Router 负责：

- `relayHub.handle_result` 在成功后广播 `task.done`；
- `relayHub.fail_task` 在失败后广播 `task.failed`；
- `taskRouter.requeue` 在重试耗尽后广播 `task.failed`；
- 定时清扫超时任务后广播 `task.failed`。

因此，`taskStore` 中没有发现“状态已改成终态但通知逻辑被吞掉”的独立缺陷。它的状态转换只接受当前四种终态，见 [`src/hub/taskStore.ts:334-336`](G:/msgrelay/src/hub/taskStore.ts:334)。

**4. 客户端代码实际上没有实现事件订阅**

[`src/client/relayClient.ts:1-18`](G:/msgrelay/src/client/relayClient.ts:1) 的说明明确写着：

- 客户端主要使用 HTTP 轮询；
- `wait_task` 通过反复调用 `GET /v1/tasks/:id` 等待终态；
- 低延迟事件场景需要另外连接 `/v1/events`。

该文件中没有 WebSocket 客户端、`subscribe` 方法或事件类型过滤逻辑。它只有：

```ts
if (is_final(task.status)) return task;
```

见 [`src/client/relayClient.ts:151-169`](G:/msgrelay/src/client/relayClient.ts:151)。

而 `is_final` 只识别：

```ts
done
failed
cancelled
expired
```

见 [`src/client/relayClient.ts:275-278`](G:/msgrelay/src/client/relayClient.ts:275)。

所以，如果已知架构描述中的“backend 通过 relayClient 订阅 Hub 事件”指的就是这个 `relayClient` 类，那么描述与当前代码不一致：**这个客户端类没有事件订阅能力，只支持轮询**。需要确认主会话实际使用的是另一个客户端实现，还是直接使用 WebSocket。

**5. Hub 的客户端事件广播没有按事件类型过滤**

客户端连接在 [`src/hub/relayHub.ts:484-513`](G:/msgrelay/src/hub/relayHub.ts:484) 建立后：

- 默认 `client.tasks` 是空集合；
- 空集合表示接收全量任务事件；
- 客户端发送 `{type:'subscribe', taskId}` 后，才限制为指定任务。

实际过滤逻辑在 [`src/hub/relayHub.ts:521-531`](G:/msgrelay/src/hub/relayHub.ts:521)：

```ts
if (client.tasks.size && event.taskId && !client.tasks.has(event.taskId)) continue;
```

这里没有按 `task.done`、`task.failed` 或其他事件类型过滤。因此，**Hub 没有发现“成功事件被客户端类型过滤掉”的代码路径**。

但有三个明确的丢失点：

1. 客户端不在线或 WebSocket 还没进入 `OPEN` 状态时，事件直接跳过；
2. `ws.send` 出错时只捕获异常，不记录、不重试；
3. `/v1/events` 没有事件重放机制。

设计文档明确说明 `/v1/events` 只推送订阅之后发生的事件，断线期间不会补发，见 [`docs/已知限制.md:89-94`](G:/msgrelay/docs/已知限制.md:89)。

这可以解释“之前偶尔收到过 interrupted/partial，后来 succeeded/failed 收不到”的间歇性表现：通道本身存在，但事件可能发生在订阅前、重连期间，或者客户端连接当时已经不是可写状态。

**6. 事件订阅的任务过滤也可能导致单个任务事件被丢弃**

如果主会话先发送了：

```json
{"type":"subscribe","taskId":"任务A"}
```

之后却等待任务 B，那么由于 [`src/hub/relayHub.ts:525`](G:/msgrelay/src/hub/relayHub.ts:525) 的过滤条件，任务 B 的终态事件不会发送给该连接。

这属于客户端订阅状态或任务 ID 关联问题，需要通过运行时日志确认：

- 客户端连接 ID；
- subscribe 的 taskId；
- Hub 广播时的 taskId；
- 客户端收到的 event.taskId。

**7. interrupted、partial 不是当前 Hub 的标准终态事件**

当前 Hub 的事件类型列表和代码中没有 `task.interrupted` 或 `task.partial`。代码中能确认的任务事件是：

- `task.queued`
- `task.started`
- `task.progress`
- `task.done`
- `task.failed`
- `task.cancelled`
- `task.expired`

因此此前收到的 `interrupted`、`partial` 很可能来自：

- 主会话自身的事件系统；
- Codex/OpenCode 执行节点的另一套事件；
- 上层 backend 对 Hub 事件的二次转换；
- 或 `task.progress` 的 `note/delta` 被重新解释。

仅从当前 Hub 代码不能证明这些事件由 Hub 直接广播，也不能据此判断 Hub 丢失了它们。

**最终判断**

可以确定的代码问题：

1. 当前协议没有 `task.succeeded` 或 `task.completed`，成功事件名称是 `task.done`。
2. `relayHub.handle_result` 只判断 `frame.ok === false`，不判断 `frame.status`。
3. `relayClient.ts` 没有事件订阅实现，只有 HTTP 轮询。
4. 事件通道没有重放、确认或重试，断线和订阅时序会导致事件丢失。
5. WebSocket 发送失败被静默忽略。
6. 任务订阅按 taskId 过滤，订阅错任务 ID 会直接收不到终态事件。

目前不能仅凭静态代码确认的部分：

1. Codex/OpenCode 实际上报的是 `ok`，还是 `status=succeeded/completed/failed`。
2. 主会话实际监听的是 `task.done`，还是等待 `task.succeeded/task.completed`。
3. 事件丢失时客户端是否已经连接并完成订阅。
4. 是否发生过 taskId 或 generation 不匹配。
5. `partial/interrupted` 是否属于 Hub 事件，还是上层自定义事件。

建议修复顺序：

1. 先抓一条真实节点上报的 `result` 原始 JSON，确认 `ok/status` 字段。
2. 在主会话侧打印实际监听的事件名称。
3. 在 Hub 的 `handle_result`、`publish_task_event`、`publish`、客户端 subscribe 处理处增加结构化日志。
4. 统一终态协议：推荐继续以 `done/failed/cancelled/expired` 为内部和 Hub 标准名称，并让主会话兼容 `task.done`。
5. 如果必须兼容外部的 `succeeded/completed`，在 `handle_result` 或 `publish_task_event` 做显式状态映射，并增加对失败状态的严格解析。
6. 为关键终态增加查询兜底：收到事件后再次调用 `GET /v1/tasks/:id`；重连后主动查询未完成任务，避免依赖不可重放的 WebSocket 事件。
