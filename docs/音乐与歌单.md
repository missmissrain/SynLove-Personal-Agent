# 音乐：点歌与歌单连播（v1.3.3）

目标：**"想听什么"能真的响起来**，而且不靠截图点界面。

## 为什么不用 GUI 自动化

最早的做法是截图 + 点坐标控制酷狗桌面客户端。问题是：窗口位置、弹窗广告、
登录态一变就全乱，而且和"用 GUI 控其它软件"的技能抢同一套动作，路由会打架。
现在 GUI 路线已经删掉，只保留**媒体键**做传输控制（见技能 `windows-media-key-playback-control`）。

## 现在的链路

```
欣爱（工具调用）
   │  kugou_search / kugou_play / kugou_play_playlist
   ▼
kugou/mcp/kugouMcp.py            MCP stdio，工具入口
   ▼
kugou/client/kugouApi.py         本地 KuGouMusicApi（3001）：搜索、歌单、取播放地址
kugou/client/MusicQueue.py       服务器曲目队列与补页
kugou/client/RemoteMusicPlayback.py  通过终端API派发播放
   ▼
扬声器
```

- 上游 **KuGouMusicApi** 只提供元数据与播放地址，它**不能**让酷狗客户端播某首歌；
  所以"点歌"是"API 取地址 + 本地播放器播"。
- 首次使用要先装上游并登录一次（见 `kugou/README.md`）。
- 这套东西也有独立仓库 **[synlove-kugou](https://github.com/missmissrain/synlove-kugou)**（含 `install_api.py`、上游链接与反风控说明），可以脱离本项目管理器的其它部分单独跑。

## 工具

| 工具 | 说明 |
|---|---|
| `kugou_search` | 搜歌（歌名 / 歌手 / hash） |
| `kugou_play` | 点一首并立即播放 |
| `kugou_playlists` | 列登录账号的歌单 |
| `kugou_playlist_tracks` | 看某歌单里有哪些歌（只读） |
| `kugou_play_playlist` | **播放整个歌单**：逐首取地址 + 自动连播 |
| `kugou_control` | play / pause / next / prev / stop |
| `kugou_status` | 服务、登录、当前在放什么 |
| `kugou_login` | 生成登录二维码（VIP/付费歌需要） |

## 歌单连播怎么做到"不触发风控"

**绝不批量请求播放地址**——这是酷狗最容易判定异常的地方。具体做法：

1. 取歌单曲目：一页 30 首**元数据**（不含 URL）；
2. 只对**当前这一首**请求 `/song/url`，拿到地址立刻开始播；
3. 一首播完（ffplay 进程退出）→ 再为下一首请求地址；
4. 队列走到页尾，才补下一页元数据（`refill`）；
5. 单曲之间强制最小间隔 ≥1 秒，失败进 30 分钟冷却。

实测：手动杀掉当前 ffplay 模拟"播完"，`index` 从 0 自动变 1，新进程拉起第二首。

## 音质与失败降级

| 情况 | 行为 |
|---|---|
| 音乐包账号 + 有 flac | 直接播**无损**（默认 `quality=flac`） |
| flac 不可用 | 自动降 `320` → `128`，回复里注明"mp3" |
| 需要 VIP / 未登录 | 返回"需要登录"，走 `kugou_login` 扫码 |

两个容易踩的坑（都写进技能里了）：

- **cookie 必须原样拼进 URL，不能 URL 编码**：服务端按 `;` 切分，编码成 `%3B` 会报"本次请求需要验证"；
- 取地址时 `album_audio_id` 传 `0` 才会返回真 flac；传搜索结果的 Audioid 会被降级成 mp3。

## 暂停是"真暂停"

`pause` 用 Windows 的 `NtSuspendProcess` 挂起 ffplay 进程，`play` 再恢复——
不是杀进程重放，所以进度不会丢。

## 边界

- 一次最多连播 50 首（`limit`），可让欣爱改；
- 同一时刻只有一条播放队列，新点歌会替换当前队列（避免两路声音打架）;
- 歌单是"登录账号自己的歌单"，别人的分享链接目前不支持。
