# 稳定性与兜底（v1.3.5）

这一版主要解决两类"长跑会死"的问题：**多个实例互相踩**、**微信/QQ 卡住不回**。

## 1. 单实例硬锁（防多开）

多实例的后果不是"慢"，而是：两个进程抢同一个 QQ 网关（`op=7` 互踢、循环重连）、
两个消费者抢同一个微信游标（消息卡在 `routing` 再也不往前走）。

现在任何启动路径都要先过两道关（`config/startHarnessBackend.ps1`）：

| 关卡 | 机制 | 好处 |
|---|---|---|
| 命名互斥体 | `Global\SynLoveHarnessSingleton` | 进程被强杀时系统会自动释放（abandoned mutex），不会留死锁 |
| 端口检查 | 3080 已监听就直接退出 | 连 node 都不启动，省掉一次启动风暴 |

QQ 网关还有 `~/.dsh/qq-gateway.pid` 作为第二道防线（跨进程也不会双连）。

> 之前"越兜越乱"的真正原因不是没锁，而是**判活代码在中文 Windows 上解码崩溃**：
> `subprocess.run(text=True)` 按 UTF-8 解 GBK 输出 → 抛异常 → 被当成"实例死了" → 反复重启。
> 现在所有子进程调用都显式 `encoding="utf-8", errors="replace"`。

心跳看门狗发现 3080 DOWN 时也会走这个脚本，所以它同样绕不过互斥体。

## 2. 微信：游标卡死自愈

微信入站协调器的规则是"投递到终态才提交游标"。如果 harness 在 `routing` 阶段被重启，
没人收尾 → 游标永远不动 → 后面所有消息都进不来（表现为"不回消息但进程还活着"）。

三层兜底：

| 层 | 位置 | 行为 |
|---|---|---|
| 启动时 | `start_stack.py::clear_stuck_deliveries()` | 把残留 `routing` 标终态，立刻释放游标 |
| 运行中 | `tools/guardService.py` | 非终态投递超过 **10 分钟** → 标 `failed_terminal` |
| 出箱 | 同上 | `sending` 超过 **5 分钟** → 允许重试（30 分钟窗口内） |

## 3. QQ：网关挂了能回来

- `guardService` 每 60 秒看 `qq-gateway.pid` 是否还活着，不在就重启栈；
- 网关自己遇到连续被踢（`op=7`）**5 次**后冷却 **5 分钟**再 Identify，避免"被踢—重连—再被踢"的死亡螺旋；
- 重连时先 `op=7` 清 session 再 Identify，不会因为旧 session 一直被拒。

## 4. 微信 ingress 静默检测

`runtime/weixin-probe.log` 里如果 **5 分钟**没有任何 `poll.*` 事件，说明长轮询已经死了
（连接假活）。`guardService` 判定后重启整条栈，带 **10 分钟冷却**，避免重启风暴。

这是"看着像正常、其实收不到消息"这类故障唯一有效的发现手段——端口和进程都是好的。

## 5. 巡检进程自己也要有人看

| 机制 | 频率 | 覆盖 |
|---|---|---|
| `guardService.py --loop` 常驻 | 每 60 秒 | 投递/出箱/租约/QQ/RSSHub/微信静默/技能复盘补跑 |
| 计划任务 `SynLoveGuard` | 每 5 分钟 | 常驻进程挂了也能兜一次（`--once`） |
| 计划任务 `SynLoveConsoleWatch` | 每 5 分钟 | 控制台/看门狗自身的存活 |

巡检做的事都是**幂等**的：同一轮重复跑不会把状态改坏。

### 巡检还要负责"定时任务没跑成"

定时任务不是万能的：进程可能崩、可能被杀、可能被文件占用拌住（2026-10-29 03:00 的技能复盘就这样）。
所以巡检每轮都看一次 `runtime/skill-review-state.json` 的水位：**越过应跑时刻（默认 03:00）十分钟**还没成功，
就自己补跑一轮，30 分钟冷却防抖，并用 `runtime/skill-review.lock` 保证不会和计划任务并排跑。

写文件的底层也换成了"重试 + 降级副本"（`skills/store/durableFile.py`）：主文件被占用就写
`*.locked-<时间戳>.bak`，一行不丢，也绝不抛异常把进程带崩。细节见 `docs/技能沉淀.md` 最后一节。

日志也按"谁写谁的文件"分开：程序写的结论进 `*.log`，进程的 stdout/stderr 进 `*.console.log`。
两个句柄写同一份文件正是那次崩溃的直接原因，所以启动器里全部拆开。

## 6. 启动顺序与"停不干净"

- 启动：清死租约 → 清卡住投递 → 起 harness → 起 Gemma → 起提醒服务 → 起 RSSHub → 起巡检；
- 停止：先写 `runtime/guardian.pause` 让守护让路，再停后端（否则守护会在关机过程中把后端拉回来）；
  完全停止用 `tools/stop_all.cmd`（先前端、再后端）。

## 7. 观测

| 文件 | 看什么 |
|---|---|
| `runtime/harness-run.log` | `gateway READY` / 重连 / 模型故障转移 |
| `runtime/weixin-probe.log` | `poll.*`、`cursor.committed`（判活依据） |
| `runtime/guard-service.log` | 本轮巡检结论与自愈动作 |
| `runtime/reminder-service.log` | 提醒是否按时推送 |
| `runtime/rsshub.log` | 新闻源是否可用 |

判断"卡死"的最短路径：**看 `guard-service.log` 有没有释放投递，看 probe 有没有 poll 事件**。

## 8. 启动时闪黑框：根因与规矩（2026-11-02）

**现象**：双击 SynLove 快捷方式，会出现一个黑色控制台窗口，开屏动画结束后它自己消失。

**根因**：不是 Electron，也不是 `.cmd` 快捷方式。是后台进程"**没有控制台**"时，
它每拉起一个控制台程序（PowerShell、tasklist、git、MCP 的 python、schtasks），
Windows 都会为那个子进程**新建一个可见控制台窗口**。巧的是这些调用多在启动阶段批量发生，
启动完成就停了，于是看起来像"窗口跟着开屏动画一起消失"。

用 `tools/ScanConsoleWindows.py` 抓到的真实血缘（修复前）：

- `powershell.exe ← pythonw.exe ← pythonw.exe ← node.exe(server.mjs) ← electron.exe`
- `tasklist.exe ← pythonw.exe ← …`
- `cmd.exe ← node.exe(RSSHub) → git.exe`（RSSHub 拉取路由时）
- `python.exe(MCP：video/selfMemory/kugou) ← node.exe(harness)`

**两条规矩，改后台启动代码时必须遵守**：

1. 后台父进程要 `CREATE_NO_WINDOW`（不可见控制台），**不要 `DETACHED_PROCESS`**。
   DETACHED 会让父进程彻底没有控制台，子孙进程就会各自新建可见窗口。
2. 会再拉起子进程的 Python 用 `python.exe`，**不要 `pythonw.exe`**。
   pythonw 是 GUI 子系统程序，永远没有控制台，同样会把黑窗传给它的子进程。

统一入口：`services/ProcessLaunch.py`（`run_hidden` / `spawn_hidden` / `console_python`）。
Python 侧与 Node 侧（`windowsHide: true`，且不加 `detached: true`）都走这套约定。

**验证方法**（可复现）：干净停栈后运行
`python tools/ScanConsoleWindows.py --seconds 75 --interval 40`，再双击快捷方式。
输出末尾必须是 `可见控制台窗口 0 个`。

**同一个窗口"闪一下又没"的第二个原因**：启动器还在等 3080/3081 时，
控制台侧又收到一次"重启后端"，重启会写 `runtime/guardian.pause`，
正在跑的启动器把它误判成"用户要停"，于是自我取消、白等 120 秒。
现在 `console/server.mjs` 在启动请求后 90 秒内忽略重启请求。

**顺带修掉的连通性问题**：`detect_local_proxy()` 原来只看端口有没有人监听，
本机 1080 被系统服务占用（不是代理）时会被误判成 Clash，微信 iLink 与 QQ 网关
的出站请求全部走死代理，表现为"能收不能发 / 一直重连"。现在会真的发一次
`CONNECT` 验证代理可用，否则直连。
