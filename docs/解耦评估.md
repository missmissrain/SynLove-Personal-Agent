# 解耦评估（2026-11-28）

对照 `架构总览.md` 第 6 节列出的 8 个原始耦合点，逐项给出当前状态与证据。

## 总体结论

| 维度 | 重构前 | 现在 |
|---|---|---|
| 代码库 | 4 个大库平铺在根目录 | `repos/` 下 5 个库，各库独立根 |
| 项目绝对路径（.py/.ps1/.cmd） | 352 处 / 163 文件 | 0 处（计划任务参数除外） |
| 中转节点实现 | 3 份 | 1 份 `relayNode`（+1 份终端协议节点） |
| 设备清单出口 | 多处直读 devices.json | `DeviceRegistry` 唯一出口 |
| 事实状态出口 | 多处读写 runtime/*.json | `facts` 服务（8802）统一 API |
| 设备管理归属 | 终端库 | `backend-service/fleetService` |
| 配置位置 | 各库 `config/` | 真实文件在 `models/config/`，统一解析 |
| 数据/技能 | 混在 runtime | `data/`、`skills/` 独立目录 |

## 逐项状态

### 1. 跨仓库 sys.path 导入

重构前：`tools/`、`scripts/`、`presenceState/` 里大量 `sys.path.insert` 指向终端库。

现在：跨库注入只剩 7 处，且都集中在入口脚本或惰性导入：

- `personal-agent/remoteControl/TerminalServerRuntime.py:31` → `backend-service`
- `personal-agent/screenInitiative/screenTerminal.py:79` → `backend-service`
- `personal-agent/scripts/runFactsService.py:8-9` → `terminal-pc`、`backend-service`
- `personal-agent/scripts/runGatewayService.py:9` → `terminal-pc`
- `terminal-pc/scripts/ProvisionTerminal.py:14`、`scripts/RunTerminal.py:40` → `backend-service`

**残余风险：中。** 仍是编译期耦合，没有走 HTTP/SDK 边界。

### 2. 文件即接口

重构前：`runtime/voiceRouting/{presence,listening,reasoning}.json` 被语音、屏幕、推理、控制台多方读写。

现在：在场/监听事实由 `facts` 服务（8802）统一暴露 `/v1/facts/*`；但 `presenceState/SnapshotStore.py` 仍同时写
`runtime/presenceState/` 与 `runtime/voiceRouting/reasoning.json`，`voiceRouting/AudioRouteStore.py` 仍写
`runtime/voiceRouting/state.json`。

**残余风险：高。** 写入方没有完全收敛到 facts 服务，仍是文件即接口。

### 3. 语音链路耦合路由

重构前：`voicePipeline` 直接 import `voiceRouting` 与 `screenInitiative`。

现在：`voice/runVoiceGateway.py` 仍直接导入 5 个领域模块：

`voice.voiceGateway`、`voice.voicePipeline`、`screenInitiative.screenInitiative`、`voiceRouting.AudioRouteService`、`voiceRouting.ListeningRouteService`、`presenceState.StateMonitor`。

**残余风险：高。** 这是目前最重的一处耦合，语音进程仍是一个「什么都知道」的组合根。

### 4. 在场判断两套

`screenInitiative/PresenceInference.py`（规则）与 `presenceAgent/PresenceModelClient.py`（模型）并存，结论互相覆盖。

**残余风险：中。** 规则作为兜底可以保留，但两套结论缺少单一裁决点。

### 5. 中转节点三份实现

现在只有 `backend-service/relayNode` 承载模型节点与业务节点（两份配置），
`terminal-pc/terminalConnection/server/RelayServerNode.py` 承载 `terminal.connection` 能力。

**残余风险：低。** 两份代码但职责不同，协议一致。

### 6. 配置分裂

`screenInitiative.json` 与 `audioRouting.json` 仍同时存在 `devices` 键；`allowSpeaker` 只在 `screenInitiative.json`。

**残余风险：中。** 设备白名单没有单一来源，改一处容易漏另一处。

### 7. 状态分散

`graph`、`timeline` 已独立到 `data/`；`runtime/dsh` 仍是会话/附件/凭据的混合目录；
SQLite 状态库（weixin/qq/terminal）分属各服务。

**残余风险：中。** 数据目录已分层，但「谁拥有哪份状态」仍需在文档中固定。

### 8. 启动与 supervisor

仍有 38 个计划任务，入口脚本已相对化，但没有统一的 supervisor 与健康总览。

**残余风险：中。** 单个服务失败仍要靠看门狗各自恢复。

## 新增耦合（拆库引入，需知悉）

`backend-service/fleetService` 依赖终端库的 4 个公共件：

- `terminalConnection.privacy.TransientResults`
- `terminalConnection.privacy.CommandPrivacy`
- `terminalConnection.security.DeviceIdentity`
- `terminalConnection.completion.NoticeText`

这是「后台 → 终端库」的编译期依赖。推荐下一步把这几件下沉到 `sdk`，
让 fleetService 只依赖 SDK，不再依赖终端库。

另外，17864 设备管理仍由 `personal-agent` 的 CoreService 进程内托管
（`TerminalServerRuntime`），进程边界尚未独立。

## 建议的下一步（按收益排序）

1. 把 `voice/runVoiceGateway.py` 拆成 HTTP 组合根：路由/在场只调 8802 与 8812 的接口，不再 import 领域模块。
2. 让 `SnapshotStore` 只通过 facts 服务写在场结论，停止直写 `runtime/voiceRouting`。
3. 把 fleetService 依赖的 4 个终端公共件下沉到 `sdk`。
4. 设备白名单统一到一份配置（建议 `models/config/devices.json`）。
5. 17864 独立成 `fleetService` 进程，CoreService 只保留客户端。
