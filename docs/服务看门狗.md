# 服务看门狗

## 定位

**唯一实现**：`facts/ServiceWatchdog.py`，跑在事实服务进程（8802）里。
它只回答一个问题：**此刻哪些服务在线**。在线状态的判定、重启动作、状态快照都只有这一处。

## 判定规则

| 项 | 默认 | 说明 |
|---|---|---|
| `intervalSeconds` | 30 | 每轮探活间隔 |
| `failThreshold` | 2 | 连续失败多少次才判离线（避免瞬时抖动） |
| `restartCooldownSeconds` | 300 | 同一个服务两次拉起的最小间隔 |
| `maxRestartsPerHour` | 3 | 一小时内最多拉起几次，超过就只报警不再动手 |
| `timeoutSeconds` | 3 | 单次探测超时 |

探活方式：配置了 `url` 走 HTTP 健康检查（2xx/3xx 视为在线），只配 `port` 走 TCP 连接。
有 `task` 字段的服务可被拉起（`schtasks /run`）；没有 `task` 的只报告，不动手。

## 配置

`config/watchdog.json`：

```json
{
  "intervalSeconds": 30,
  "failThreshold": 2,
  "services": [
    {"name": "message", "url": "http://127.0.0.1:8805/health", "task": "SynLove-MessageGateway"},
    {"name": "tts", "port": 7862, "note": "ModelHub 管理，只报告"}
  ]
}
```

## 接口

- `GET /v1/facts/services`：当前快照（在线数、离线列表、每个服务的失败次数与最近错误）
- `POST /v1/facts/services/check`：立即跑一轮，返回同样结构

## 产物

- `runtime/facts/services.json`：最近一轮快照，可直接看
- `runtime/facts/watchdog.log`：只在状态变化与拉起时写一行，不刷屏

## 仍独立的部分

| 组件 | 为什么不在看门狗里 |
|---|---|
| `guardService` | 做的是链路修复（清死租约、释放投递、清卡住的 outbox），不是「在不在线」 |
| `backend-watchdog.ps1` | 托管业务进程的启停，属于业务运行时自身生命周期 |
| `SynLoveTerminalKeeper` | 终端侧保活，跑在终端仓库 |
